# Агент-объяснитель решений САП

Read-only ИИ-агент, который объясняет пользователю решения системы автоматического
планирования производства: почему заказ попал на эту линию, почему стоит в этом месте
очереди, почему готов позже срока, почему снят по нормативно-справочной информации.
Агент ничего не меняет — он собирает проверяемые факты из первичных источников и
показывает, на чём построен вывод. При расхождении источников он не выносит вердикт
сам, а готовит черновик обращения в поддержку.

Система под наблюдением — стенд `../demo_bko` (обезличенная демо-версия планирования
БКО, все данные синтетические). Агент читает её **снаружи**, только по путям из
`config/settings.yaml`: никаких импортов кода стенда. Благодаря этому ту же папку
можно положить рядом с боевой инсталляцией, поменяв одну секцию конфига.

> Статус: собран целиком. Работают граф выполнения, девять read-only инструментов,
> векторная память с гибридным поиском, прогон золотого набора, замеры моделей и
> интерфейс.

## Схема архитектуры

```
                        вопрос пользователя
                                 │
                    ┌────────────▼────────────┐
                    │ ingest                  │  guardrails · request_id · read-only
                    └────────────┬────────────┘
                    ┌────────────▼────────────┐
                    │ classify        M_fast  │  класс вопроса + сущности → строгий JSON
                    └────┬───────────────┬────┘
             неоднозначно│               │ intent + сущности
                    ┌────▼─────┐    ┌────▼────────────────┐  этап → нормы → таблицы
                    │ clarify  │    │ stage_context  код  │  → код, по индексам и
                    └────┬─────┘    └────┬────────────────┘  графу связей, без модели
                         │          ┌────▼────────────────┐
                         │          │ plan_sources router │  какие источники нужны
                         │          └────┬────────────────┘
                         │          ┌────▼────────────────┐   read_task · read_plan
              ┌──────────┼─────────►│ act    M_balanced   │◄──lookup_nsi · read_logs
              │          │          │        M_code       │──►search_regulations
              │          │          └────┬────────────────┘   search_code
              │          │          ┌────▼────────────────┐
              │          │          │ observe M_balanced  │  хватает ли доказательств
              │          │          └────┬───────────┬────┘
              └──────────┼───────────────┘           │ достаточно
                мало фактов, ≤5 итераций   ┌─────────▼──────────┐
                         │                 │ check_consistency  │  M_reason
                         │                 └──┬────────┬────────┘
                         │       противоречие │        │ подтверждено
                         │              ┌─────▼───┐ ┌──▼──────┐
                         │              │ ticket  │ │ answer  │
                         │              └─────┬───┘ └──┬──────┘
                    ┌────▼─────────┐        ┌─▼────────▼─┐
                    │ insufficient │        │ verify     │  M_reason: каждое
                    └────┬─────────┘        └─────┬──────┘  утверждение → источник
                         │                   ключевое│замечание
                         │                  ┌───────▼────────┐
                         │                  │ answer (правка)│ один заход
                         │                  └───────┬────────┘
                         └────────────┬─────────────┘
                                 ответ пользователю
```

Четыре условных ребра — неоднозначность запроса, достаточность доказательств,
вердикт сверки, итог проверки — и два обратных: `observe → plan_sources` (набор
инструментов растёт вместе с понятыми пробелами) и `verify → answer` (ключевое
замечание проверки возвращает ответ на переписывание, один раз). Роль модели
закреплена за узлом: дешёвая работает на входе, сильная — только на сверке
источников и финальной проверке.

Узел `stage_context` модель не вызывает вообще. Он проходит «этап → нормы этапа →
таблицы НСИ, на которые они ссылаются → функции, которые эти таблицы читают» по
индексам и графу связей и печатает карту в задание сбора. Причина простая:
живые прогоны показали, что модель угадывает номера таблиц и по четыре круга
просит «таблицу, которую читает ExtrusionStage.run», — то есть ровно те связи,
которые уже посчитаны при сборке памяти. Обход идёт с двух сторон, и разница
множеств сама показывает кандидатов в расхождения: норма называет параметр,
которого в коде этапа нет. На стенде это находит пропуск диаметра кольца в
отборе линий кольцевания (ТР-КОЛ п. 5.1 против `demo/ringing.py`) без участия
модели — ту самую ошибку, на которой модель в прогоне 3 сделала обратный вывод.

## Установка

### Что нужно до начала

**Стенд `demo_bko` — обязателен, и в этот репозиторий он не входит.** Агент читает
его снаружи как чужую систему и без него не работает: читать будет нечего. Стенд
лежит отдельно — <https://github.com/vegorovmsk/demo-bko> — и это не деление ради
порядка: агент не импортирует из него ни строчки, поэтому в настоящей установке на
место стенда встаёт боевая система, а агент остаётся прежним. Два репозитория
делают это свойство проверяемым, а не обещанным.

Положите их рядом:

```
AI_2026_06/
├── demo_bko/        ← стенд: данные, регламенты, код расчёта, config.yaml
└── sap_agent/       ← этот репозиторий
```

Путь задаётся в `config/settings.yaml`, секция `stand` — если стенд лежит в другом
месте, поменяйте там `root`, остальное подтянется. Проверить, что агент видит стенд:
`python -m app.runner --selftest`.

Ещё понадобится **Python 3.10 или новее** и **ключ OpenRouter** (для облачного
профиля) либо **Ollama** (для локального). Ключ кладётся в `.env` и в репозиторий
не попадает — `.env` в `.gitignore`.

### Шаги

```bash
pip install -r requirements.txt
cp .env.example .env             # заполнить OPENROUTER_API_KEY
python -m llm.probe --config     # живы ли объявленные модели и умеют ли инструменты
docker compose up -d qdrant      # необязательно, см. ниже
python -m memory.build           # собрать индексы регламентов и кода
python -m app.runner --selftest  # сквозная проверка: стенд, память, модели
```

Порядок не случаен. `llm.probe` стоит перед сборкой памяти намеренно: у провайдера
модель может быть объявлена и при этом не иметь ни одного маршрута с поддержкой
инструментов, и узнать об этом лучше за десять секунд, чем из трассы неудавшегося
прогона. `--selftest` в конце отвечает на вопрос «а всё ли вообще собралось»:
читается ли стенд, каким эмбеддером собрана память, отвечают ли модели профиля.

**Qdrant.** Память живёт в Qdrant. Сервер поднимать не обязательно: если
`QDRANT_URL` пуст, клиент работает во встроенном режиме и хранит данные в
`memory/store/qdrant`. Разница одна — встроенный режим не создаёт индексы по
payload, что на корпусе в сотни фрагментов незаметно, а на тысячах уже нет.
С сервером доступна и веб-панель на <http://localhost:6333/dashboard>, где видно
коллекции и точки — удобно, когда разбираешься, что именно нашёл поиск.

Встроенный Qdrant держит метаданные в SQLite, поэтому на сетевом или
синхронизируемом каталоге он падает с `disk I/O error`. Если это ваш случай —
поднимите сервер, укажите `QDRANT_PATH` на локальный диск либо переключитесь на
запасной бэкенд: `SAP_AGENT_MEMORY_BACKEND=numpy`.

Без Ollama индекс тоже соберётся: `python -m memory.build --fallback` использует
запасной лексический эмбеддер. Он не семантический и годится только для того,
чтобы пайплайн работал на машине без моделей. Состояние индексов показывает
`python -m memory.build --stats`, бэкенд на один запуск переключает
`python -m memory.build --backend numpy`.

Для локального профиля дополнительно нужен запущенный Ollama и загруженные модели:

```bash
ollama pull qwen2.5:7b-instruct        # M_fast
ollama pull qwen2.5:14b-instruct       # M_balanced и M_reason
ollama pull qwen2.5-coder:7b           # M_code
ollama pull bge-m3                     # эмбеддинги — нужны во ВСЕХ профилях
```

`bge-m3` нужен и облачному профилю: эмбеддинги держатся локально, потому что корпус
внутренний и отправлять его наружу незачем. Без Ollama память соберётся запасным
лексическим эмбеддером (`--fallback`), но семантического поиска не будет — это
режим «чтобы запустилось на машине без моделей», а не рабочий.

## Проверка качества: золотой набор

```bash
python -m evals.run_evals --profile cloud        # все кейсы
python -m evals.run_evals --group B              # только расхождения
python -m evals.run_evals --only A1,C1
```

Четырнадцать кейсов в `evals/cases.yaml`, разбитых на четыре группы: **A** —
решение системы корректно и агент должен это доказать; **B** — регламент и код
расходятся, агент должен выйти на обращение в поддержку; **C** — дефект данных,
различимый только инструментом; **N** — отрицательные, где правильный ответ это
уточняющий вопрос или честный отказ.

Проверяется не гладкость текста, а обоснованность: тот ли выбран маршрут, те ли
источники прочитаны, названы ли обязательные координаты, совпал ли статус с
эталоном — и отдельно, не прозвучали ли запрещённые формулировки. Последнее
ловит именно то, ради чего всё затевалось: правдоподобную выдумку вроде «линия
была занята профилактикой».

Отчёт пишется в `evals/report.md` и `evals/report.json`, а каждый кейс оставляет
свою трассу в `observability/runs/`.

## Выбор моделей: замеры

Перед прогоном стоит убедиться, что объявленные модели вообще живы и умеют
инструменты:

```bash
python -m llm.probe            # кандидаты на роль
python -m llm.probe --config   # модели, объявленные в models.yaml
```

Проверка делает по одному настоящему вызову с объявленным инструментом и говорит,
годится модель или нет. Появилась она не от хорошей жизни: прогон 13.09 потерял
14 кейсов из 19, потому что у провайдера не нашлось маршрута с поддержкой
инструментов, а прогон 14.09 состоялся, но роль `M_code` все 47 раз падала в
запасную модель — то есть в конфиге стояла мёртвая, и узнали мы об этом из трассы
постфактум. Состав ролей нужно проверять, а не предполагать.

Дальше — сами замеры:

```bash
python -m llm.bench --models or_fast,or_balanced,or_reason,or_code
```

Меряются ровно те способности, от которых зависит работа агента: строгий вывод по
JSON-схеме при разборе запроса, точность определения намерения и номера заказа,
вызов инструмента через function calling, задержка и стоимость. Отчёт —
`docs/bench.md`; он и есть ответ на вопрос, почему в конфиге именно эти модели.

Устойчивость к выдумкам и работа с длинным контекстом этим замером не ловятся —
их проверяет прогон золотого набора.

## Интерфейс

```bash
streamlit run app/streamlit_app.py
```

Показывает не только ответ, но и то, как он получен: доказательную базу с
координатами, ход рассуждения по шагам графа, выбранный маршрут и стоимость
прогона.

Инструменты можно вызывать напрямую, без модели — удобно для отладки и для
демонстрации доказательной базы:

```bash
python -m app.runner --tool read_plan  --args '{"order_number": "Z-1060"}'
python -m app.runner --tool lookup_nsi --args '{"table": "18", "filters": {"Вид печати": "Флексо-4"}}'
python -m app.runner --tool lookup_nsi --args '{"table": "29", "filters": {"Вид": "Синтекс", "Тип": "Ск"}}'
python -m app.runner --tool search_code --args '{"clause": "ТР-КОЛ п. 5.1"}'
```

Последняя команда показывает, зачем агенту инструмент, а не поиск по документам:
норматив не находится, потому что в таблице ключ записан латинской `C` (U+0043)
вместо кириллической `С` (U+0421). Глазами строки неразличимы.

Каждый прогон оставляет файл трассы `observability/runs/<request_id>.jsonl`.

## Живой прогон: порядок действий

> **После правки индекса память надо пересобрать.** Хранение полного текста
> фрагментов изменило формат содержимого, поэтому первым шагом идёт
> `python -m memory.build`. Без пересборки `search_code` продолжит отдавать
> прежние обрезанные тела функций.


```bash
pip install -r requirements.txt
# вписать OPENROUTER_API_KEY в .env любым редактором — в консоль ключ не вводить
python -m memory.build --fallback                 # собрать индексы (один раз)
python -m app.runner --profile cloud --selftest   # проверка готовности
python -m app.runner --profile cloud "Почему заказ Z-1060 не поставлен на линию ЛП2?"
```

Первый прогон делайте профилем `cloud`: профиль `hybrid` (он по умолчанию) держит
роли `M_fast` и `M_balanced` на Ollama, и без запущенного Ollama он не стартует.
Когда локальные модели будут подняты, `--fallback` при сборке индексов тоже не
нужен: эмбеддинги пойдут через `bge-m3`, и поиск станет семантическим, а не
лексическим.

`--selftest` проверяет не только доступность моделей. Он отдельно пробует то, на
чём настоящие модели спотыкаются чаще всего: строгий JSON по схеме и вызов
инструмента через function calling. Если эти две строки зелёные, граф почти
наверняка пройдёт целиком. Флаг `--shallow` пропускает пробные вызовы и не тратит
токены.

### Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| `not a valid model ID` | Идентификаторы моделей в `config/models.yaml` — кандидаты. Сверьте с openrouter.ai/models и поправьте строку нужной роли |
| `BadRequestError` про `response_format` | Модель не поддерживает строгую JSON-схему. Поставьте ей `supports_json_schema: false` — клиент перейдёт на `json_object` со схемой в системном сообщении и валидацией на своей стороне |
| «инструменты не вызваны» в самопроверке | Модель роли `M_balanced` не умеет function calling или игнорирует его. Смените модель роли; на корректность графа это не влияет — `--tool` работает без моделей |
| `не вернула ни одного варианта ответа` у роли | OpenRouter при отказе апстрима отвечает HTTP 200 и кладёт причину в поле `error`, оставляя `choices` пустым. Сообщение показывает причину провайдера дословно; сам вызов повторяется, потому что «нет свободного провайдера» и лимиты обычно временные. Если повторяется устойчиво — модель роли недоступна, замените её в `config/models.yaml` |
| `Индекс собран эмбеддером ollama:bge-m3, а поиск откатился на запасной` | Ollama не отвечает. Индекс пересобирать НЕ нужно — запустите `ollama serve` и повторите. После перехода на настоящий эмбеддер он нужен на каждом прогоне, а не только при сборке; `--selftest` проверяет это заранее отдельной строкой |
| `APITimeoutError` при сборке памяти на эмбеддингах | Пачка фрагментов уходит одним запросом и считается на сервере последовательно, а на процессоре это минуты. У эмбеддингов свои лимиты: `limits.embed_timeout_s` (300 с на запрос), `limits.embed_batch` (8 фрагментов), `limits.embed_retries`. Если всё равно не успевает — уменьшите пачку. Повторная сборка безопасна: коллекции пересоздаются целиком, недособранный индекс не остаётся |
| `already accessed by another instance of Qdrant client` | Это встроенный режим, значит `QDRANT_URL` пуст. Встроенный Qdrant держит каталог монопольно: ни второй python, ни Streamlit, ни незакрытый прошлый прогон рядом с ним работать не могут. Если сервер поднят — впишите `QDRANT_URL=http://localhost:6333` в `.env`; если сервер не нужен — закройте процесс, который держит каталог |
| `disk I/O error` при сборке памяти | Встроенный Qdrant не работает на сетевом или синхронизируемом каталоге. Поднимите сервер (`docker compose up -d qdrant`), укажите локальный `QDRANT_PATH` или переключитесь на `SAP_AGENT_MEMORY_BACKEND=numpy` |
| Прогон встал на лимите стоимости | Потолок задан в `config/settings.yaml`, ключ `limits.max_cost_usd` |
| Прогон стоит на одном узле дольше минуты | Так было до правки: таймаут SDK считает паузы в передаче, а не общее время, и сверка источников однажды длилась 332 с. Теперь поверх стоит жёсткий дедлайн `limits.hard_timeout_s`; в трассе он виден событием `llm.timeout` |
| В ответе ссылка на непрочитанный источник | Механическая проверка координат ловит это в узле `answer`: сначала модели прямо называют выдуманную координату и просят переписать, потом фраза с ней вычёркивается. В трассе — `evidence.invented_locators` со статусом `repair_requested` или `struck` |

После прогона в `observability/runs/<request_id>.jsonl` лежит полная трасса: какой
маршрут выбран, какие инструменты вызваны с какими аргументами, сколько токенов и
денег потрачено, что решил каждый узел. Это же файл-артефакт для сдачи.

## Память: что агент помнит и чего не помнит

Памятей три, и они разного назначения.

| вид | где живёт | что помнит | между вопросами |
|---|---|---|---|
| долговременная | Qdrant: 102 пункта регламентов, 70 функций кода | знания о наблюдаемой системе | сохраняется |
| рабочая | `AgentState` внутри прогона | факты с координатами, пробелы, что уже читал, какие вызовы не удались | сбрасывается |
| журнал | JSONL-трасса, файл на прогон | весь путь: узлы, роли, вызовы, решения | пишется, но обратно не читается |

Памяти о **разговоре** у агента нет, и это решение, а не недосмотр. Один случай
всё же замкнут: если прогон закончился уточняющим вопросом, ответ пользователя
склеивается с исходной формулировкой (`app/followup.py`), и в консоли это
выглядит как обычный диалог — агент спросил, вы ответили, он продолжил. Раньше
уточнение было тупиком: на «Z-1060» начинался новый прогон, который не знал, о
чём сам спрашивал минуту назад.

Между ходами переносится **только формулировка вопроса**. Факты — нет, и здесь
проходит принципиальная граница. Главная гарантия агента в том, что каждое
утверждение ответа снабжено координатой источника, прочитанного В ЭТОМ прогоне, и
что механические проверки этого прогона эту координату видели. Унаследованный
факт такой координаты не имеет: он взят из чужой доказательной базы. Память о
разговоре вправе помнить, ЧТО спрашивали; помнить, что при этом выяснилось, она
не вправе — иначе через два хода ответ будет опираться на утверждения, которых
никто не перепроверял.

Полноценный follow-up («а почему не ЛК1?» после ответа) не сделан сознательно: он
требует переносить в `classify` контекст прошлого хода, а это тот самый узел,
точность маршрута которого мерена золотым набором. Правильная реализация — хранить
последние 2–3 хода как краткую сводку «о чём шла речь» и подмешивать её к
классификации, оставляя сбор фактов нетронутым.

## Показ вживую

Порядок вопросов для демонстрации — от быстрого к содержательному. Времена из
итогового прогона (`evals/report.md`), профиль `cloud`.

| # | Вопрос | ~время | Что показывает |
|---|---|---|---|
| 1 | `Почему заказ не туда встал?` | 2 с | Агент не догадывается, а переспрашивает: номера заказа нет, дорогие модели не тронуты |
| 2 | `Где находится заказ Z-1001?` | 39 с | Простой путь: два чтения, ответ с координатой строки расписания |
| 3 | `Где находится заказ B-3007 и есть ли по нему просрочка?` | 37 с | Честное «в расчёте его нет»: отсутствие записи — тоже факт, а не повод фантазировать |
| 4 | `Учитывается ли диаметр кольца при отборе линии кольцевания?` | 50 с | **Главный кейс.** Норма требует, код не исполняет; расхождение находит обход по индексам, а не мнение модели, и оно превращается в черновик обращения в поддержку |
| 5 | `Объясни действующие ограничения на экструзии` | 128 с | Вопрос без номера заказа: этап → нормы → таблицы → код, собранные детерминированно |
| 6 | `Почему заказ Z-1020 вообще не попал в план?` | 81 с | Объяснение отказа со ссылкой на пункт регламента и таблицу НСИ |

На что смотреть в консоли во время ответа: агент печатает трассу по ходу работы —
видно, какой узел работает, какая роль вызвана, какой инструмент и с какими
аргументами, сколько это заняло. Это и есть ответ на вопрос «почему я должен вам
верить»: каждое утверждение в ответе снабжено координатой, а путь до него виден
целиком.

Если заданный вживую вопрос не сложится, агент скажет `insufficient` и назовёт,
чего не хватило. Это не отказ демонстрации, а её часть: агент, который на любой
вопрос отвечает уверенно, не годится для объяснения решений — проверить его будет
нечем.

## Закрытый контур: что нужно и чего ждать

Два независимых шага: сервер Qdrant вместо встроенного режима и Ollama вместо
запасного эмбеддера. Второй важнее — он исправляет то, что сейчас не работает.

**Qdrant сервером.** Всё уже разведено, нужен только запуск:

```
docker compose up -d qdrant          # порты 6333 (REST и панель) и 6334 (gRPC)
# в .env:  QDRANT_URL=http://localhost:6333
#          QDRANT_API_KEY=           ← локальному серверу ключ не нужен
python -m memory.build
python -m memory.build --stats       # бэкенд должен стать серверным
```

Что даёт: появляются индексы по payload (`к_планированию`, `этап`, `документ`,
`файл`, `chunk_id`) — встроенный клиент их игнорирует; хранилище уезжает в том
контейнера, и вместе с ним исчезает весь класс отказов `disk I/O error`, которым
встроенный Qdrant отвечает на синхронизируемый или смонтированный каталог;
появляется панель `http://localhost:6333/dashboard`, где индекс видно глазами.
На 172 фрагментах прироста скорости не будет, на тысячах будет. После переезда
каталог `memory/store/qdrant` можно удалить.

**Ollama для эмбеддингов — нужен всегда, в том числе в профиле `cloud`.**
Роль `embeddings` во всех трёх профилях локальная: корпус регламентов и кода
внутренний, наружу его отдавать незачем. Если Ollama не запущен, сборка индекса
откатывается на `HashingEmbedder` — символьные n-граммы, — и в логе появляется
`! эмбеддер hashing-1024`. В этом состоянии смысловая половина гибридного поиска
не работает вовсе: находится только то, что совпало буквально. Номера пунктов и
таблиц так ищутся хорошо, перефразированные формулировки — нет.

```
ollama pull bge-m3
python -m memory.build               # в логе «эмбеддер ollama:bge-m3», без отката
```

Сборка на процессоре — минуты, и это единственная длинная операция в проекте,
поэтому у эмбеддингов свои лимиты (`limits.embed_timeout_s`, `embed_batch`,
`embed_retries`) и свой прогресс в выводе. Пачка уходит одним запросом и
считается на сервере последовательно: мерить её таймаутом одного
интерактивного вызова неправильно, и на этом сборка один раз уже упала. Если
`bge-m3` на вашем процессоре окажется слишком медленным, более лёгкая
многоязычная замена — `multilingual-e5-small` (около 118M против 568M), ценой
качества поиска по русскому тексту.

Индекс обязательно пересобрать, а не просто переключить: имя эмбеддера записано
в хранилище, и поиск чужим вектором отвергается с `StoreError`. `bge-m3` — 568M
параметров, это работа для процессора: разово закодировать корпус — секунды,
запрос — один короткий текст. Видеокарта не нужна.

**Генерация локально — демонстрация контура, а не режим работы.** Модели профиля
`local` приведены к ноутбучным размерам (`qwen2.5:7b-instruct`,
`qwen2.5:14b-instruct`, `qwen2.5-coder:7b`); прежний `qwen3:32b` в роли
`M_reason` требовал около 20 ГБ и на ноутбуке не поднимался вовсе. Но и с
ноутбучными размерами на машине без видеокарты ждите десятки минут на один
вопрос: прогон — это 10–15 вызовов модели, а каждый вызов сначала жуёт 3–6 тысяч
токенов задания. Сверх скорости есть риск важнее: у всех локальных моделей
`supports_json_schema: false`, клиент деградирует до `json_object` со схемой в
системном сообщении, и маленькие модели на этом ломаются — облачная 32B
`qwen-2.5-coder` уже дисквалифицирована замером ровно за это.

Отдельная ловушка: **Ollama обрезает промпт до `num_ctx` молча**. Поэтому перед
локальным прогоном серверу задаётся длина контекста, а `--selftest` проверяет её
функционально — кладёт метку в начало длинного промпта и смотрит, дошла ли она:

```
$env:OLLAMA_CONTEXT_LENGTH=8192; ollama serve     # PowerShell
python -m app.runner --profile local --selftest   # строка «длина контекста»
python -m llm.bench --models ollama_fast,ollama_balanced
```

Замер кладёт локальные модели в ту же таблицу `docs/bench.md`, что и облачные:
строгий JSON, верное намерение, вызов инструмента, задержка, нулевая стоимость.
Если 7B не держит схему — это измеренная граница закрытого контура на таком
железе, и в таком виде её и надо предъявлять, а не обещать словами.

Профиль `hybrid` на машине без видеокарты окажется медленнее облачного: он
отдаёт локальным моделям `M_fast` и `M_balanced`, а это самые частые роли.
Рабочий режим — `cloud`, в нём эмбеддинги всё равно локальные.

## Профили моделей

Роли — `M_fast` (класс вопроса и сущности), `M_balanced` (объяснение одного заказа),
`M_reason` (сверка источников и проверка ответа), `M_code` (разбор Python-логики),
плюс эмбеддинги для векторной памяти. Профиль задаётся в `.env` переменной
`SAP_AGENT_PROFILE` или ключом `default_profile` в `config/models.yaml`:

Роль в профиле может указывать не одну модель, а **цепочку**: первая основная,
остальные запасные. Это не украшение — полный прогон 13.09 потерял 14 кейсов из
19, потому что у OpenRouter временно не нашлось провайдера с поддержкой
инструментов для основной модели роли. Запасная выбирается с другим апстримом,
иначе общий отказ накроет всю цепочку. Переключение видно в трассе событием
`llm.fallback`, и оно происходит только на недоступности: ошибка запроса другой
моделью не лечится.

| Профиль | Что где | Зачем |
|---|---|---|
| `local` | все роли на Ollama | закрытый контур на своём сервере, нулевая стоимость |
| `hybrid` | частое и дешёвое локально, рассуждение и код в OpenRouter | рабочий режим по умолчанию |
| `cloud` | все роли в OpenRouter | быстрая разработка и верхняя планка качества для замеров |

OpenRouter и Ollama говорят по одному протоколу, поэтому на оба провайдера хватает
одного клиента: меняются только `base_url`, ключ и заголовки. Идентификаторы облачных
моделей в `config/models.yaml` — кандидаты; окончательный выбор делает `llm/bench.py`
по замерам на кейсах стенда (этап Э5).

## Что уже устроено правильно

**Ограничения.** Лимиты собраны в `config/settings.yaml`: 5 итераций цикла, 10 вызовов
инструментов, 2 обращения к векторному поиску, повторы, таймаут запроса и жёсткий
дедлайн поверх него, потолок стоимости прогона. У клиента моделей есть повтор с экспоненциальной паузой и circuit breaker:
после трёх отказов подряд провайдер размыкается на минуту — видно в выводе
`--selftest`, если Ollama не запущен.

**Трасса.** `observability/trace.py` пишет JSONL по строке на событие: шаг, роль и
модель, краткое структурированное обоснование выбора, инструмент и его безопасные
аргументы, статус, длительность, токены, стоимость, найденные источники, повторы.
Скрытая цепочка рассуждений не пишется; ключи вырезаются, длинные поля обрезаются.

**Доказательность.** В `agent/state.py` факт (`Evidence`) не существует без координаты
источника: лист и строка, номер пункта регламента, функция и файл. Утверждение без
координаты в ответ не попадёт — это проверяет узел `verify` на этапе Э6.

**Ветвление.** Первое условное ребро графа уже есть: если в запросе не хватает ключевой
сущности, агент задаёт один уточняющий вопрос вместо того, чтобы выбрать заказ наугад.

**Инструменты.** Четыре read-only читателя стенда с JSON-схемами для function calling:
`read_task` (что просили), `read_plan` (что система сделала), `lookup_nsi` (норматив
как доказательство, с посимвольной диагностикой промаха ключа), `read_logs` (что
происходило по ходу расчёта). Единый конверт ответа `{status, source, payload,
locators, error, hint}`, валидация аргументов по схеме до обращения к файлам, один
повтор при занятом файле, лимит вызовов на вопрос. Ни один инструмент не выносит
вердикт: они возвращают строки или их отсутствие, а объясняет граф. Полный SOP —
`docs/sop_tools.md`.

**Память.** Векторизуются только тексты: регламенты чанками по нумерованным
пунктам, код чанками по функциям с границами из AST. Нормативные таблицы и
результат расчёта в индекс намеренно не попадают — это структурированные данные,
к ним точечный доступ инструментами; иначе модель начнёт вспоминать числа
приблизительно.

В каждой точке Qdrant лежат два вектора: плотный эмбеддинг и разреженный BM25.
Нормативный текст держится на точных обозначениях — «Флексо-4», «ЛП2»,
«приложение 5», — а плотная модель их размывает: для неё «Флексо-2» и «Флексо-4»
почти одно и то же. Выдачи объединяются по RRF на стороне базы. Русские
словоформы приводятся к общей основе упрощённым усечением окончаний: без него
«приложение» и «приложению» для BM25 разные термины и половина совпадений
теряется.

У RRF своя шкала, несопоставимая с косинусом, поэтому решение «нашлось ли
релевантное» принимается по двум признакам отдельно от ранжирования: плотная
близость выше порога **или** лексическое попадание термина запроса. Отбрасывать
точное совпадение обозначения по плотному порогу означало бы перечеркнуть смысл
разреженной половины.

Поверх индексов лежит граф связей «пункт регламента ↔ таблица НСИ ↔ функция»,
собранный из разделов «Приложения» и обращений к таблицам в коде: он превращает
вопрос «где реализована норма 5.1» из поиска по эмбеддингам в переход по ребру.
Retrieval ограничен двумя обращениями на вопрос, и неудачные считаются тоже.

## Структура

```
sap_agent/
├── config/       settings.yaml (пути к стенду, лимиты) · models.yaml (роли → провайдер)
│                 routing.yaml (намерение → маршрут → обязательные источники)
├── core/         config.py — загрузка конфигурации, пути стенда, allow-list
├── llm/          client.py — единый клиент OpenRouter/Ollama, function calling,
│                 структурированный вывод, повторы, circuit breaker, учёт стоимости
├── observability/ trace.py — JSONL-трасса прогона
├── agent/        state.py · graph.py · router.py · guardrails.py · locators.py
│                 nodes/ (12 узлов) · prompts/
├── app/          runner.py — headless-запуск · streamlit_app.py — интерфейс
├── tools/        9 read-only читателей стенда + реестр с allow-list и лимитами
├── memory/       Qdrant и numpy, разреженный BM25, индексы регламентов и кода,
│                 links.py — граф «пункт ↔ таблица ↔ функция»,
│                 traversal.py — обход «этап → норма → таблица → код» без модели
├── evals/        cases.yaml (золотой набор) · metrics.py · run_evals.py · отчёты
└── tests/        5 наборов: smoke, tools, memory, graph, evals
```

## Соответствие требованиям курса

Сверка по «Описанию проектной работы» и «Памятке». Каждая строка закрыта файлом,
командой или прогоном — полный разбор с координатами вынесен отдельно.

| Требование | Чем закрыто |
|---|---|
| 1. Кейс и сценарий «вход → обработка → результат» | Кейс 1 «Агент поддержки» в производственной постановке; разделы «Схема архитектуры» и «Пример запроса» выше |
| 1. Цикл Reason → Act → Observe | `plan_sources → act → observe` с обратным ребром `observe → plan_sources`; 12 узлов, 4 условных ветвления |
| 1. Выбор моделей для ≥2 типов задач | 4 роли (`M_fast`, `M_balanced`, `M_reason`, `M_code`) × 3 профиля; выбор подтверждён замером `docs/bench.md` |
| 1. Схема архитектуры в README | первый раздел этого файла |
| 2. Минимум один инструмент | девять read-only инструментов, `tools/registry.py` |
| 2. Function calling с валидацией | JSON-схемы `tools/schemas.py`, проверка аргументов до вызова, allow-list |
| 2. SOP использования | `docs/sop_tools.md` + описания функций, которые видит модель |
| 2. Обработка ошибок вызова | пять статусов результата, повторы, и сбойный вызов возвращается модели с подсказкой |
| 3. Векторная память | Qdrant, плотный + разреженный вектор, RRF; 102 пункта регламентов и 70 функций кода |
| 3. Семантический поиск (RAG) | `memory/search.py`, релевантность по косинусу и лексическому попаданию |
| 3. Управление retrieval агентом | `plan_sources` решает, нужен ли поиск; пробел добавляет инструмент на следующей итерации; квота 6 |
| 3. Связи и гибридный поиск *(необязательно)* | граф «пункт ↔ таблица НСИ ↔ функция», обход этапа `memory/traversal.py` |
| 4. Последовательность 3–5 шагов | 12 узлов графа LangGraph |
| 4. Минимум одно ветвление | четыре, все в `agent/router.py`, без обращения к модели |
| 4. SDK / LangGraph / n8n | LangGraph `StateGraph`, состояние-датакласс, узлы возвращают дельты |
| 5. Метрики успеха, времени, стоимости | золотой набор из 19 кейсов, 8 метрик, `evals/report.md`; история прогонов с разбором — `evals/history/` |
| 5. Логирование и трассировка | JSONL с `request_id`, 12 видов событий, покрыты все 14 пунктов памятки |
| 5. Ограничения | 14 лимитов: итерации, вызовы, стоимость, повторы, таймаут, жёсткий дедлайн, circuit breaker |
| 5. Проверка вывода | механическая сверка координат, переписывание ответа, вычёркивание неподтверждённого |
| 5. Устойчивость к сбоям | цепочки запасных моделей по ролям, память о недоступных моделях, деградация суждения вместо падения прогона (`agent/nodes/judgement.py`) |
| Форма сдачи | публичный репозиторий, README, пример запроса и результата |

Сознательно не реализовано из необязательного: MCP, streaming, мультиагентность,
n8n, облачный деплой, голосовой интерфейс.
